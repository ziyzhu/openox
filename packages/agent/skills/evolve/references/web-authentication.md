# Website Sessions and Login

A session is a currently authenticated website context, not an open page, remembered account, or Ox-created record. Preserve existing login state. Never sign out, clear website data, or repeat login solely for testing. Pages share the Host's existing persistent website data store; they do not isolate accounts.

## Standard actions

Authenticated web services implement both `listSessions` and `login`. Inspection advertises their Host access helpers instead of duplicating them in the business-action index; the implementations remain invokable for compatibility. Mark protected actions `requireAuth: true`; the Host requires a selected descriptor and fresh account discovery instead of a generic boolean probe. Public actions use `requireAuth: false`. Session discovery and login require both `requireAuth: false` and `requireApproval: false`. The old getSignInUrl/getSignInState contract is unsupported.

`listSessions` takes a closed empty input object. Route tenant-specific discovery with top-level `pageUrl`, or derive the target from the selected page and second-argument `session` context. Its output schema is an array whose items are closed objects requiring string properties `id`, `label`, and `url`. Every value is nonempty. `id` identifies an authenticated account and its independent tenant scope, not a browser position, generic "current" placeholder, or token. `label` distinguishes accounts for the user. `url` is a public HTTPS entry point within the service domain that selects that context without credentials. Never include cookies, tokens, signatures, passwords, or reusable secrets.

Discover sessions using observed authoritative account selectors or authenticated endpoints. Website SDK authentication errors can trigger navigation, logout, or prompts; use observed request options that suppress those global effects during discovery without disabling authorization or server checks. Suppress SDK credential/header logging for identity requests. Return only currently authenticated contexts. A confirmed signed-out response returns `[]`; an unclassified status, remembered signed-out account, malformed response, CORS/network failure, or unsupported discovery must not be treated as an authenticated session or an empty list. Do not switch accounts or mutate user data during discovery. Multi-tenant discovery may require an employer or resource URL; do not claim a global directory exists when only one tenant was checked.

`login` accepts the target/account-selection inputs actually needed by the site and returns `null` after preparing the interaction. Its handler can open dialogs, click account-selection controls, or navigate to an observed login route. Preserve tenant and resource return paths and all supported login options. Never guess a login path or accept credentials in arguments. The Host presents the same live page after preparation, waits for user completion, and preserves it. Cancellation throws. Completion acknowledges interaction only; use `ox.service.checkAccess` afterward to discover sessions. There is no automatic detector or authentication polling.

## Execution

Use the applicable `access.checkAccess` and `access.requestAccess` contracts from `ox.service.inspect` for discovery and login. The Host dispatches the service's `listSessions` and `login` implementations. Website login inputs belong in requestAccess.input; its schema comes from the service's login action. For tenant discovery or login, optional top-level `pageUrl` selects an observed initial public HTTPS URL within the service domain. It is not an authenticated session. Stop capture and clear injected scripts before handing login to the user; never use Browser's generic interaction handoff for authentication.

Copy a returned descriptor into top-level `session` for subsequent invocations. Do not combine `session` and `pageUrl`. The Host validates routing and selects one live execution page for that session context; actions on it are serialized. Task arguments remain in `input`. A handler may receive `async invoke(args, { session })`; the descriptor is selection intent, not proof that access remains valid. The Host reruns read-only `listSessions` in the selected page before ordinary selected-session actions and rejects a stale, missing, or altered descriptor before dispatch. This checks availability, not that every endpoint uses the intended account. Verify the actual account and tenant before account-sensitive work and reject mismatches without silently falling back to another account.

Reuse a selected descriptor across actions; do not add discovery before every invocation because the Host revalidates it. Rediscover after login, expiry or an account switch. Public actions may execute without a session. When several accounts are available, select using the user's request or ask if ambiguous. If access expires, discover again or request login rather than inventing a signed-out session. Shared cookies can change from another page. Never infer current authentication from a cached descriptor or cookie presence alone.

Use `ox.service.showPage` with the same action name, input and top-level `session` or `pageUrl` to show its existing page without reloading or repeating effects. Showing the page returns immediately and does not reserve it against subsequent actions. End the turn for human verification or payment; inspect fresh state after the user reports completion. Inspect uncertain mutations before retrying; never automatically repeat writes after login.

## Repair existing services

Treat an unsupported authentication contract as a normal service repair. Read the source even if the service cannot load, inspect current website evidence, and implement the standard actions above. Do not mechanically rename the old pair or invent account IDs from a boolean. Preserve unrelated Local edits, task contracts, and website data. Verify account-sensitive handlers actually use their selected account, validate the replacement, and reattach through the normal authoring workflow. No separate migration flow is needed.

API credentials, OAuth callbacks, and native OS permissions retain their existing contracts. Human verification and payment use ordinary service actions and ox.service.showPage; website login does not authorize payment or replace transaction review.
