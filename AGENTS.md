If you are an agent, do not edit this file.

## General Rules

1. Keep enough structured logs to diagnose production issues.
1. Do not use code comments; communicate through code.
1. Prefer small, simple changes; consider refactoring as you work.
1. Model state explicitly, prefer state machines that make illegal states unrepresentable over scattered booleans.
1. Always work on `main` branch.
1. Keep documentation minimal; prefer code as the source of truth; avoid nested sections in md.
1. Improve existing user/project skills or steering files when you identify useful lessons.
1. AGENTS.md should not reference skills, vice versa, they should stay independent.
1. Do not introduce new abstractions without permission for simple changes.
1. UX must hold up across supported devices and use equal outer-edge padding.
1. Reference Apple development documentation for iOS changes.
1. For animation, check [Animate with springs](https://developer.apple.com/videos/play/wwdc2023/10158/).
1. Keep temporary screenshots, recordings, traces, and diagnostics outside the repository.
1. App Store Connect owns listing metadata and media, do not repeat.
1. UI components should have stable automation/accessibility identifiers and apply them to the actual controls.
1. Reuse the configured iOS bundle identifier for simulator builds and installs.
1. No source code file should be >2000 lines or >50 KB, use a lint rule to enforce this.
1. Close the simulator after you are done using it.

If you are fixing an issue:
1. reproduce it first in a simulator
1. verify that it can no longer be reproduced
1. after fix, do not add unit tests.
1. ensure no regressions

If you are working on a new feature:
1. ensure no regressions

If you are refactoring:
1. ensure no regressions

If you are commiting:
1. skip below if the change is tiny or doesn't affect the source code.
1. build the targets to prevent checking in bad changes.
1. review lines of code and cyclomatic complexity.
1. review the performance implications.
1. show the lines-of-code (LOC) delta, file tree diff, and call stack diff; mark non-applicable diffs explicitly.
1. review the backward compatibility, if any, show the endpoints affected and on-device storage layout in a diff block.
1. (if it is a UI change) capture screenshots or videos from the simulator and share for visual review.
1. do not include `Co-Authored-By` trailers in commit messages.

Commit template:

```text
<imperative summary>

Changes:
- <what changed and why>

Testing:
- <checks performed and results>

Related:
- <related references or None>
```

After you push a change:
1. monitor CI, if failed, fix it and push again.

## OpenOx Rules

1. The app must remain neutral to LLM provider.
1. Logs are user-owned on-device diagnostics.
1. When OpenOx functionality uses OAuth, use apps registered as OpenOx.
1. Keep system skills self-contained and free of external links.
1. Keep agent prompts and bundled System skills in `packages/agent`.
1. `README.md`, `OnboardingView.swift`, and the openox website should be consistent.
1. Always require user confirmation before destructive actions.
1. Hosted service and model-provider icons live only in the `openox-service-assets-prod` S3 bucket.
1. Reuse the fixed `ox-1`–`ox-5` simulator pool for all simulator work.
1. Secrets should never be exposed to Ox as plain text, only via references.
